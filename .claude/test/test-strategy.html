DCT MCP Server — Automated Test Strategy

Replacing manual Claude Desktop verification with a layered automated test suite
Status: Proposal Repo: delphix/dxi-mcp-server Date: 2026-05-22

Overview

The Problem

Every code change is verified by hand through Claude Desktop. A developer manually drives prompts from .claude/test/testing/<toolset>.md, visually inspects responses, and writes a free-text report. This doesn't scale, isn't reproducible, doesn't gate merges, and requires a live DCT instance.

The Core Insight — Two Different Questions

The manual Claude Desktop check is actually answering two different questions at once. Conflating them is what makes the process so heavy.

Question 1: Regression

Given input X, does the workflow chain still produce Y after a code change?

Answered by: scripted workflow tests, no LLM
Question 2: AI usability

Can an AI figure out how to use these tools from descriptions alone?

Answered by: LLM-driven exploratory tests

Solve them separately. Regression goes in CI on every PR. AI usability is an optional, local-only, pre-release check.

Architecture

Three layers in CI form the regression gate. One optional layer runs locally to answer the AI-usability question.

┌──────────────────────────────────────────────────────────────┐ │ Layer 1 — Unit (in-process, mocked client) │ │ tool fn → MagicMock(DCTAPIClient).make_request │ │ ~60% of tests · seconds │ ├──────────────────────────────────────────────────────────────┤ │ Layer 2 — Integration (in-process, mocked HTTP) │ │ tool fn → DCTAPIClient → httpx → respx intercept │ │ ~25% of tests · seconds │ ├──────────────────────────────────────────────────────────────┤ │ Layer 3 — Functional (subprocess + stub DCT) │ │ 3a. Toolset registration (5 personas, parametrized) │ │ 3b. ★ Workflow tests — .md scenarios translated to Python │ │ 3c. Confirmation handshake over MCP wire │ │ ~15% of tests · ~60 seconds │ ├──────────────────────────────────────────────────────────────┤ │ Layer 4 — E2E vs. real cloned DCT │ │ Same workflows, real instance, on-demand via GitHub UI │ │ Manual trigger primary; nightly cron optional │ ├──────────────────────────────────────────────────────────────┤ │ Layer 5 — LLM-driven (LOCAL ONLY, optional) │ │ LM Studio → MCP server → dct_stub │ │ AI-usability check · not in CI · not blocking │ └──────────────────────────────────────────────────────────────┘

Layer 3b is the centerpiece

Workflow tests translate each chain in your existing .claude/test/testing/*.md files into one deterministic Python test. This is what directly replaces the manual Claude Desktop playbook.

Why three layers in CI?

Each layer catches a class of bugs the others can't see:

  • Unit proves routing logic, but says nothing about whether the HTTP request you'd build is correct.
  • Integration proves the wire format (URLs, headers, retries), but says nothing about whether the server even boots.
  • Functional proves the server boots, registers the right tools, and works over MCP stdio — including full multi-step workflows.

Workflow Tests — The Centerpiece

The pattern in one paragraph

Each multi-step chain in .claude/test/testing/<toolset>.md becomes one Python test function. The chaining ("that VDB" → previous result) becomes a Python variable. Each step is a real MCP call over stdio via fastmcp.Client. Each step is verified at the wire level via dct_stub.received_request(...). No LLM in the loop — deterministic, fast, reproducible.

Example — translating self_service.md lines 12–17

The original manual prompts:

1. Search for all VDBs
2. Get the details of the first VDB from the previous result
3. Start that VDB
4. Stop that VDB

The translated test:

# tests/functional/workflows/test_vdb_lifecycle.py
async def test_vdb_lifecycle_start_stop(mcp_client, dct_stub):
    # Step 1 — Search for all VDBs
    vdbs = await mcp_client.call_tool("vdb_tool", {"action": "search"})
    assert vdbs["items"], "search returned no VDBs"
    vdb_id = vdbs["items"][0]["id"]

    # Step 2 — Get details of the first one
    details = await mcp_client.call_tool("vdb_tool", {"action": "get", "vdbId": vdb_id})
    assert details["id"] == vdb_id

    # Step 3 — Start that VDB
    await mcp_client.call_tool("vdb_tool", {"action": "start", "vdbId": vdb_id})
    assert dct_stub.received_request("POST", f"/dct/v3/vdbs/{vdb_id}/start")

    # Step 4 — Stop that VDB
    await mcp_client.call_tool("vdb_tool", {"action": "stop", "vdbId": vdb_id})
    assert dct_stub.received_request("POST", f"/dct/v3/vdbs/{vdb_id}/stop")

Why scripted, not LLM-driven, for the regression gate: "Did the workflow break?" is a deterministic question. An LLM driver introduces randomness exactly when you want the opposite. Reserve LLMs for the separate, optional question: "Can an AI use these tools?" — see the LLM Testing tab.

Layer 1 Unit Tests

What this layer proves

How

    client = MagicMock(spec=DCTAPIClient)
    client.make_request = AsyncMock(return_value={"job_id": "j-1"})

    r1 = vdb_tool(action="delete_vdb", vdbId="vdb-1")

    client.make_request.assert_not_called()

    r2 = vdb_tool(action="delete_vdb", vdbId="vdb-1", confirmed=True)
    client.make_request.assert_called_once_with("DELETE", "/vdbs/vdb-1", ...)

Layer 2 Integration Tests

~25% of suite · runtime: seconds · run on every push
▶

What this layer proves

  • URL built right (base URL join, /dct/v3/ prefix, no double slashes)
  • Auth header has the apk prefix
  • 4xx fails fast, 5xx retries with exponential backoff
  • Connection errors retry
  • Query-param serialization and timeout config

How

respx intercepts httpx calls at the socket. No subprocess, no stub server.

async def test_delete_vdb_two_step_over_mcp(dct_stub):
    async with mcp_client(dct_stub, toolset="self_service") as c:

Layer 4 E2E vs. real cloned DCT

On-demand via GitHub UI · optional nightly cron · advisory only
▶

Reuses the Layer 3 workflow tests but points DCT_BASE_URL at your persistent cloned DCT instance instead of dct_stub. Triggered manually via GitHub Actions UI; nightly cron is optional.

Prerequisite check

The cloned DCT must be reachable from GitHub-hosted runner IPs. If it's VPN-only:

  • Expose it via a tunnel (Cloudflare Tunnel, ngrok) for tests
  • Or use a self-hosted GitHub runner inside the network that hosts the DCT
  • Or fall back to local-only execution (developer runs pytest tests/e2e on a VPN-connected machine)

One-time setup

  1. Repo settings → Secrets → add DCT_TEST_BASE_URL and DCT_TEST_API_KEY
  2. Confirm cloned DCT has stable known fixture data (env, dSource, snapshot)
One runner, two contexts. Both local and CI invoke the same CLI — dct-mcp-test. See the CLI Runner tab for details.

Workflow file

# .github/workflows/e2e-real-dct.yml
name: e2e-real-dct
on:
  workflow_dispatch:             # primary: run on demand from GitHub UI
  schedule:
    - cron: "0 6 * * *"          # optional: passive drift detection

jobs:
  e2e:
    runs-on: ubuntu-latest
    env:
      DCT_BASE_URL: ${{ secrets.DCT_TEST_BASE_URL }}
      DCT_API_KEY: ${{ secrets.DCT_TEST_API_KEY }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.11" }
      - run: pip install -e ".[test]"
      - run: dct-mcp-test --layer e2e    # same command devs run locally
      - name: Notify on failure
        if: failure()
        run: # post to Slack/email — does NOT fail any PR

Cleanup strategy (critical for persistent DCT)

Because the DCT clone persists between runs, anything tests create must be cleaned up — even on failure.

  • Every test tags its created resources with E2E_RUN_TAG (e.g. e2e-12345)
  • A separate tests/e2e/cleanup/test_purge.py module runs as an if: always() step
  • Cleanup finds everything matching the current run ID and deletes it
  • Crashed runs still get cleaned up — the cleanup step is forced to run

What Layer 4 catches that Layer 3 doesn't

  • Real DCT API contract drift (endpoint shape changes upstream)
  • Real auth/permission issues against real ACLs
  • Network/timeout behavior under real latency
  • State that only exists on a real engine (snapshots, timeflows)
Layer 4 is a periodic confidence check, not a per-commit gate. Layer 3 still runs on every PR; Layer 4 runs when you want extra assurance.

The dct_stub Component

A fake DCT server that runs inside the pytest process so functional and workflow tests don't need a real DCT instance.

Why a stub (not a mock)

OptionProblem
Point at real DCTSlow, needs creds, side effects, flaky, can't run in CI
Mock httpx in the MCP serverDoesn't work — respx patches the test process, not the subprocess
Run a fake DCT in the test process✓ chosen server makes real HTTP calls, but they land on the stub

Data flow

pytest process subprocess (MCP server) ┌──────────────────────┐ ┌─────────────────────┐ │ test function │ │ vdb_tool(...) │ │ │ │ stdio │ │ │ │ ▼ │ ◀────────▶ │ ▼ │ │ fastmcp.Client │ │ DCTAPIClient │ │ │ │ │ httpx → │ │ dct_stub ◀───────────┼── HTTP ────┤ DCT_BASE_URL │ │ (Starlette, port=0) │ │ http://127.0.0.1 │ └──────────────────────┘ └─────────────────────┘

What it needs to support (for workflow tests)

  • Stateful canned data — vdbs/search returns the same fixture every time, so "the first VDB" is always v-1. No randomness.
  • Endpoint coverage — every endpoint the workflow chains touch (~30–40 routes across all toolsets)
  • Request recorder — stub.received_request("POST", "/dct/v3/vdbs/v-1/start") lets tests assert exactly what the server sent
  • Per-test response overrides — for negative cases ("what if start returns 503?") fixtures can swap responses
  • /dct/static/api-external.yaml — so the OpenAPI bootstrap in toolsgenerator/driver.py doesn't fail

Skeleton

# tests/fixtures/dct_stub.py
class DctStub:
    def __init__(self):
        self.requests = []  # records everything the MCP server sends
        self.response_overrides = {}

    async def vdbs_search(self, req):
        self.requests.append(("POST", "/dct/v3/vdbs/search", await req.json()))
        return JSONResponse({"items": [{"id": "v-1", "name": "fake-vdb"}]})

    async def vdb_start(self, req):
        path = req.url.path
        self.requests.append(("POST", path, None))
        if path in self.response_overrides:
            return self.response_overrides[path]
        return JSONResponse({"job_id": "j-1"})

    def received_request(self, method, path):
        return any(r[0] == method and r[1] == path for r in self.requests)

@pytest.fixture
def dct_stub():
    stub = DctStub()
    app = Starlette(routes=[
        Route("/dct/v3/vdbs/search", stub.vdbs_search, methods=["POST"]),
        Route("/dct/v3/vdbs/{vdb_id}/start", stub.vdb_start, methods=["POST"]),
        Route("/dct/v3/vdbs/{vdb_id}/stop", stub.vdb_start, methods=["POST"]),
        # ... ~30 more routes
        Route("/dct/static/api-external.yaml", lambda r: PlainTextResponse(STUB_YAML)),
    ])
    config = uvicorn.Config(app, host="127.0.0.1", port=0, log_level="error")
    server = uvicorn.Server(config)
    thread = threading.Thread(target=server.run, daemon=True)
    thread.start()
    stub.url = f"http://127.0.0.1:{port}"
    yield stub
    server.should_exit = True

The dct-mcp-test CLI — One Runner, Both Contexts

A single Python CLI tool that wraps pytest with the right flags, env vars, run-tag generation, and cleanup. Registered as a [project.scripts] entry point so pip install -e ".[test]" puts dct-mcp-test on your $PATH. Local invocation and CI invocation are identical.

Usage examples

Local
# Flags
dct-mcp-test \
  --base-url https://my-dct \
  --api-key abc123

# Or env vars
export DCT_BASE_URL=https://my-dct
export DCT_API_KEY=abc123
dct-mcp-test

# Single workflow
dct-mcp-test --workflow vdb_lifecycle

# Specific layer
dct-mcp-test --layer unit
CI (GitHub Actions)
- run: dct-mcp-test --layer e2e
  env:
    DCT_BASE_URL: ${{ secrets.DCT_TEST_BASE_URL }}
    DCT_API_KEY: ${{ secrets.DCT_TEST_API_KEY }}

Identical command. CI just provides env vars from GitHub Secrets. No drift between environments.

Available layers

LayerNeeds credentials?RuntimeWhat it tests
--layer unitNoSecondsAction routing, mocked client
--layer integrationNoSecondsHTTP wire (URLs, headers, retries)
--layer functionalNo~60sSubprocess + dct_stub workflows
--layer e2eYes~2–5 minReal cloned DCT

What it does internally

  1. Resolves credentials from flags or DCT_BASE_URL / DCT_API_KEY env vars
  2. Generates a unique E2E_RUN_TAG=e2e-{uuid8}-{timestamp} for the run
  3. Maps --layer to pytest paths + markers
  4. Runs pytest with the right arguments
  5. Always runs the cleanup pass at the end (unless --no-cleanup)
  6. Exits with pytest's exit code

Implementation (~50 lines)

# src/dct_mcp_server/testing/cli.py
import os, subprocess, sys, time, uuid
import click

@click.command()
@click.option("--base-url", envvar="DCT_BASE_URL", help="DCT base URL")
@click.option("--api-key", envvar="DCT_API_KEY", help="DCT API key")
@click.option("--layer",
    type=click.Choice(["unit", "integration", "functional", "e2e", "all"]),
    default="e2e", help="Test layer to run")
@click.option("--workflow", help="Filter to workflows matching this name")
@click.option("--no-cleanup", is_flag=True, help="Skip cleanup (DANGER on persistent DCT)")
def main(base_url, api_key, layer, workflow, no_cleanup):
    """Run the DCT MCP Server test suite."""
    env = os.environ.copy()

    if layer in ("e2e", "functional", "all"):
        if not base_url or not api_key:
            click.echo("--base-url and --api-key required for this layer", err=True)
            sys.exit(2)
        env["DCT_BASE_URL"] = base_url
        env["DCT_API_KEY"] = api_key
        env["E2E_RUN_TAG"] = f"e2e-{uuid.uuid4().hex[:8]}-{int(time.time())}"

    paths_by_layer = {
        "unit": ["tests/unit"],
        "integration": ["tests/integration"],
        "functional": ["tests/functional"],
        "e2e": ["tests/e2e"],
        "all": ["tests/unit", "tests/integration", "tests/functional", "tests/e2e"],
    }
    args = ["pytest", *paths_by_layer[layer], "-v"]
    if layer == "e2e":
        args.extend(["-m", "real_dct"])
    if workflow:
        args.extend(["-k", workflow])

    result = subprocess.run(args, env=env)

    if layer in ("e2e", "all") and not no_cleanup:
        click.echo("\n--- Running cleanup ---")
        subprocess.run(["pytest", "tests/e2e/cleanup", "-v"], env=env)

    sys.exit(result.returncode)

## 4. Stream output
- Show pytest output as it runs
- On failure, offer to read the failing test, propose a fix, re-run

Why Not Claude Desktop / LLM-Driven for the Regression Gate

The question keeps coming up: "can we just automate Claude Desktop?" The honest answer is no, and the reasons are worth recording so we don't relitigate them later.

Claude Desktop GUI automation — rejected

ConcernDetail
Closed Electron appNo official automation API; Playwright/AppleScript driving relies on DOM that changes between releases
Slow~10s per click; one scenario file would take 15+ minutes
Zero new signalClaude Desktop's only unique behavior is the LLM picking tools — and Desktop's LLM is the same Claude you'd hit via API more cleanly
Brittle in CIHeadless GUI in GitHub Actions is its own infrastructure project

Claude API as the driver — blocked by license + cost

ConcernDetail
Requires explicit API key Anthropic API (console.anthropic.com) is a separate product from Claude Enterprise (claude.ai with SSO). The Enterprise license covers humans using the UI; it does not include programmatic API access by default.
No key currently available Would need to be provisioned by IT/admin under the enterprise contract, or set up via AWS Bedrock / GCP Vertex AI if those exist in the org
Real cost Per scenario run: ~$2.40 without prompt caching, ~$0.50–$0.80 with caching. Full nightly run (5 toolsets): ~$12 uncached, ~$3–4 cached. Monthly: $30–$360 depending on cadence and caching strategy
Noisy signal for regression testing An LLM driver can fail a test because it got confused, not because the code regressed. This blurs failure attribution and makes flake triage expensive.

LM Studio (local LLM) — useful, but for a different purpose

LM Studio exposes an OpenAI-compatible HTTP API on localhost:1234/v1. Any code that talks to OpenAI talks to LM Studio with a base-URL swap.

from openai import OpenAI
client = OpenAI(base_url="http://localhost:1234/v1", api_key="not-needed")
response = client.chat.completions.create(
    model="qwen2.5-coder-32b-instruct",
    tools=[mcp_tool_to_openai_schema(t) for t in tools],
    messages=[{"role": "user", "content": scenario}],
)

Pros

  • $0 monetary cost
  • No API key required
  • Runs offline, fully private
  • Free for unlimited runs

Cons / tradeoffs

ConcernDetail
Model quality dictates tool-use reliability Qwen 2.5 Coder 32B = good. Llama 3.3 70B = very good. Llama 3.1 8B default = marginal. Anything <7B = unreliable.
Hardware bound 32B model needs ~20GB RAM; 70B needs ~40GB+. On 16GB you're stuck with smaller models that misfire on multi-step chains.
Cannot run in GitHub Actions GitHub-hosted runners have no GPU and limited RAM. Would require a self-hosted runner with LM Studio always running — real infra work.
Slower than hosted APIs 5–30 tok/s on a Mac vs 50–100 tok/s for Claude API
Noisier signal Same failure-attribution problem as Claude API — was it the code or the model?

Good for

  • Pre-release exploratory testing. Run before a release, see whether the AI navigates the toolsurface naturally. Catches confusing action names, vague parameter descriptions, ambiguous tool overlap.
  • Local sanity check after refactoring tool schemas. If you renamed actions or changed descriptions, LM Studio tells you if you broke discoverability.
  • Demo or showcase without cloud dependencies.

Not good for

  • The CI regression gate. Use scripted workflow tests for that — deterministic, fast, free, runs anywhere.
  • Replacing the manual playbook on a per-PR basis. Signal too noisy, infra too heavy.

The architectural separation

Regression gate

Runs on every PR

  • Layers 1–3
  • Scripted, deterministic
  • No LLM in the loop
  • $0 cost
"Did the workflow break?"
AI-usability check

Runs ad-hoc, local only

  • Layer 5
  • LLM-driven, exploratory
  • LM Studio (no API key)
  • $0 cost
"Can an AI use this tool?"
Layer 5 is completely optional. The regression-prevention goal — the one motivating this entire project — is fully met by Layers 1–3 alone. Layer 5 only adds value if/when you specifically want to test AI usability separately.

Success Criteria

After Phase 5 (merge gate replaces manual playbook)

  1. pytest runs locally with no DCT credentials and no network
  2. Every PR shows a CI status check; merges to main require it to pass
  3. Every chain in .claude/test/testing/*.md has an equivalent Python workflow test
  4. Each persona toolset has at least one functional test verifying tool registration
  5. The confirmation two-step contract has one functional test per confirmation level
  6. The .claude/test/testing.md manual playbook is reduced to exploratory testing only — never a regression check

After Phase 8 (unified runner)

  1. dct-mcp-test is on the $PATH after pip install -e ".[test]"
  2. /dct-mcp-test works from any Claude Code session
  3. CI workflow yaml uses the same dct-mcp-test command developers use locally

After Phase 9 (real-DCT validation)

  1. Real-DCT E2E runnable from GitHub UI workflow_dispatch
  2. Same suite runnable locally via dct-mcp-test --base-url ... --api-key ...
  3. Same suite runnable via /dct-mcp-test localhost --api-key ... from Claude Code
  4. Cleanup pass deletes everything tagged with the run ID, even on test failure
  5. Tool response shapes captured as syrupy snapshots; drift breaks CI

Out of Scope

  • Performance / load testing
  • Testing against multiple DCT versions in parallel
  • Property-based / fuzz testing of tool inputs
  • Visual regression of MCP client UIs
  • Claude Desktop GUI automation (see LLM Testing tab)
  • Claude API as a CI test driver (see LLM Testing tab)
