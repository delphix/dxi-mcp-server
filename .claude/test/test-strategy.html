Layer 3b is the centerpiece

Every multi-step chain in .claude/test/testing/*.md becomes one deterministic Python test. Each step is a real MCP call over stdio to the actual dct-mcp-server subprocess. The fake DCT — dct_stub — records every HTTP request and we assert the right endpoint was hit.

The .mcp.json server as single source of truth

The delphix-dct entry in .mcp.json defines the server command, args, and env. Both Layer 4 (build_real_transport) and Layer 5 (_write_mcp_config) read from it. Credentials come from DCT_BASE_URL / DCT_API_KEY env vars — never hardcoded.

Layer 3b — Workflow Tests ★ the heart

Each multi-step chain in .claude/test/testing/<toolset>.md becomes one Python test function. Chaining ("that VDB" → previous result) becomes a Python variable. Every step verified at wire level via dct_stub.received_request(...).

async def test_vdb_lifecycle_search_get_start_stop(mcp_client_self_service, dct_stub):
    search = await mcp_client_self_service.call_tool(
        "vdb_tool", {"action": "search", "limit": 10})
    vdb_id = _payload(search)["items"][0]["id"]

    await mcp_client_self_service.call_tool(
        "vdb_tool", {"action": "start", "vdb_id": vdb_id})
    assert dct_stub.received_request("POST", f"/dct/v3/vdbs/{vdb_id}/start")

    await mcp_client_self_service.call_tool(
        "vdb_tool", {"action": "stop", "vdb_id": vdb_id, "confirmed": True})
    assert dct_stub.received_request("POST", f"/dct/v3/vdbs/{vdb_id}/stop")

What a workflow test catches that nothing else does

  • "I renamed an action and the .txt config now points to a non-existent function" → DCT endpoint never gets called → stub assertion fails
  • "I edited the confirmation rule and it no longer gates stop_vdb" → first call no longer returns confirmation_required → assertion fails
  • "The stub tells me exactly which endpoint was never hit" → precise failure messages vs. "it didn't work"

The dct_stub Component

Source: tests/fixtures/dct_stub.py. A Starlette app that runs in-process during functional tests. Records every request; serves canned responses.

Data flow

pytest process │ ├─ StubServer.start() → uvicorn thread on 127.0.0.1:<random-port> │ ├─ fastmcp.Client(StdioTransport) │ spawns dct-mcp-server subprocess, DCT_BASE_URL=stub.url │ ├─ await client.call_tool("vdb_tool", {"action": "search"}) │ subprocess → HTTP POST …/dct/v3/vdbs/search │ dct_stub._record(request) ← records for assertion │ dct_stub.vdbs_search() ← returns {"items":[…]} │ └─ assert dct_stub.received_request("POST", "/dct/v3/vdbs/search")

Routes

Explicit handlers for VDB lifecycle paths (search, get, start, stop, delete, confirmation-gated endpoints). A catch-all (Route("/dct/v3/{rest:path}", …)) handles all other resources (groups, dsources, snapshots, bookmarks, jobs, timeflows, environments, engines) with shape-appropriate canned data.

Deliberately does not serve /dct/static/api-external.yaml — the server falls back to pre-built modules, giving a stable tool surface for stub-based tests.

OpenAPI spec fixture

tests/fixtures/api-external.yaml (gitignored) is downloaded from DCT_BASE_URL/dct/static/api-external.yaml on first run and cached locally. The openapi_spec session fixture in tests/functional/conftest.py downloads on demand, falling back to the cache for offline runs.

LLM Testing — Claude Code CLI as the MCP Client

Driver: Claude Code CLI only

Layer 5 uses claude -p … --output-format stream-json as the sole LLM driver. It connects to the delphix-dct MCP server defined in .mcp.json — the same server the interactive Claude Code session uses. Credentials from DCT_BASE_URL / DCT_API_KEY env vars (never hardcoded). The _write_mcp_config(toolset) helper derives command/args from .mcp.json and stamps in the requested toolset.

claude -p "<task>" \
  --mcp-config <derived from .mcp.json> \
  --strict-mcp-config \
  --allowedTools "mcp__delphix-dct__*" \
  --permission-mode bypassPermissions \
  --append-system-prompt-file .claude/test/llm-driver-preprompt.md \
  --output-format stream-json --verbose

Job-completion pre-prompt

.claude/test/llm-driver-preprompt.md instructs Claude: whenever a tool response contains a job_id, poll job_tool(action="get") until COMPLETED or FAILED before declaring success. Never report success on job submission alone. Only then run the verification step.

The act → verify pattern

PhaseWhat happensKey rule
1. ActClaude receives plain-English task, discovers and calls the toolNo tool/action names in the prompt
2. WaitPre-prompt enforces job_tool polling to COMPLETED/FAILEDNever return on job submission alone
3. VerifySeparate Claude call reads the real DCT stateIdentifier NOT in the verify prompt (prevents echo = false pass)

License tolerance

Some DCT tiers block resource types (401: License does not permit operations on VDB_GROUP). call_tool_tolerant (tests/e2e/_helpers.py) and license_blocked() (tests/llm_local/conftest.py) skip rather than fail, making both layers resilient across DCT configurations.
