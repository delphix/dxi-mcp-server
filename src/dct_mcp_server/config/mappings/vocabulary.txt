# Vocabulary translation map (PPM-1129)
#
# Applied to text that originates upstream -- raw DCT/engine error bodies and
# OpenAPI summaries -- before it is shown to a user. Internal terminology on the
# left, the canonical customer-facing term on the right.
#
# Format: internal_term|canonical_term
#
# Matching is case-insensitive and whole-word; the replacement preserves the
# capitalisation style of the match (lower, Title or UPPER).
#
# Reconciled against the real DCT_MCP_Server_Vocabulary_Glossary_v1.2.xlsx
# (28 canonical terms, 172 synonym rows). See config/server_instructions.md
# for the full domain model and for rules this flat term map cannot express
# (see "Known limitation" below).

# --- Retired/forbidden product-and-engine terms (glossary #8, #10, #28) ---
# "virtualization engine" and "masking engine" are unambiguous despite being
# forbidden -- each names exactly one of the two engine products, so a flat
# replacement is safe here (unlike bare "engine"/"Delphix engine" below).
virtualization engine|Continuous Data engine
masking engine|Continuous Compliance engine
delphix masking|Delphix Continuous Compliance
cloud engine|Elastic Data

# --- Known limitation: bare "engine" / "Delphix engine" (glossary #8) ---
# The glossary requires this to disambiguate to WHICHEVER of the Continuous
# Data engine or Continuous Compliance engine is contextually correct, and
# explicitly forbids defaulting to one. to_canonical() is a context-free,
# single-replacement term map (tools/core/vocabulary.py) and cannot make that
# judgment -- silently picking "Continuous Data engine" here would reproduce
# exactly the wrong-default bug the glossary warns against. We flag the
# ambiguity in the replacement text itself instead of silently guessing; the
# model must still resolve it from conversation context per
# config/server_instructions.md's terminology rules. Do not "fix" this by
# re-introducing a single-product default.
delphix engine|Continuous Data/Compliance engine (clarify which)
